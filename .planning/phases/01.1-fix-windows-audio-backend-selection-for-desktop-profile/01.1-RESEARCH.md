## Summary

The immediate failure is structural, not device-specific: `main.py` always instantiates `AudioRecorder` from `app.core.audio`, and that package currently exports only the ALSA `arecord` subprocess recorder (`src/app/core/audio/recorder.py`). This means a Windows-targeted profile (`platform: windows`) still enters Linux-only capture code and can fail with `arecord command not found`, matching the phase urgency.

The safest plan is to introduce explicit backend selection at recorder construction time, driven by the active profile intent (`settings.platform`) with deterministic precedence over host auto-detection. Keep the existing device-resolution pipeline in `main.py` unchanged, then branch only at recorder creation: Windows -> sounddevice/PortAudio input stream backend; Linux/RPi -> current ALSA `arecord` backend. This keeps scope narrow and preserves Pi behavior.

Testing should separate two concerns: (1) backend selection logic for platform/profile combinations, and (2) backend-specific behavior/error messages. Existing ALSA recorder tests already cover key `arecord` failure modes and should remain; add focused tests around selector wiring and Windows-path initialization/error handling.

**Primary recommendation:** Add a small recorder backend selector (profile-driven) and wire it in `main.py` without refactoring the broader audio architecture.

## Architecture Patterns

### Recommended Project Structure
```text
src/app/core/audio/
├── recorder.py              # Existing ALSA/arecord recorder (keep)
├── recorder_sounddevice.py  # New Windows-capable recorder backend
├── recorder_selector.py     # Backend selection from AppSettings/platform
├── player.py                # Existing player (unchanged)
└── __init__.py              # Export selected constructors/interfaces
```

### Pattern 1: Profile-Intent-First Backend Selection
**What:** Resolve recorder backend from `settings.platform` (and only then optional host fallback for `auto`).
**When to use:** Any startup path that can run with `--profile` override.
**Example:**
```python
def select_recorder_backend(platform: str) -> str:
    normalized = platform.lower()
    if normalized in {"windows"}:
        return "sounddevice"
    if normalized in {"linux", "rpi"}:
        return "arecord"
    if normalized == "auto":
        # fallback only when profile did not specify target
        return detect_host_default_backend()
    raise ValueError(f"Unsupported platform: {platform}")
```

### Pattern 2: Preserve Device Resolution Contract
**What:** Keep `resolve_device()` and default-device lookup in `main.py` as the single integration point.
**When to use:** While introducing backend split without breaking existing config.
**Example:**
```python
input_device = resolve_device(settings.audio.input_device or settings.audio.input_device_index, is_input=True)
# pass result directly into chosen backend constructor
```

### Pattern 3: Backend-Specific Error Wrapping, Shared Exception Type
**What:** Each backend catches native errors and raises `AudioDeviceError` with backend-relevant suggestion text.
**When to use:** Recorder startup and early stream/process failures.

### Anti-Patterns to Avoid
- **Global hardcoded recorder class:** Causes Windows profile to execute Linux-only `arecord` code path.
- **Selector based only on host OS:** Breaks deterministic `--profile` launches.
- **Changing player path in this phase:** Unnecessary risk; phase scope is recorder backend selection.

## Common Pitfalls

### Pitfall 1: Import Path Ambiguity (`app.core.audio` package vs `audio.py` module)
**What goes wrong:** Edits accidentally target `src/app/core/audio.py` while runtime imports package `src/app/core/audio/`.
**Why it happens:** Both paths exist; deferred cleanup item notes duplication.
**How to avoid:** Restrict phase edits to `src/app/core/audio/` package + `main.py` wiring only.
**Warning signs:** Tests pass for mocked classes but runtime wiring unchanged.

### Pitfall 2: Losing ALSA string device support on Pi
**What goes wrong:** New validation coerces Linux `plughw:X,Y` strings into invalid numeric-only path.
**Why it happens:** Treating all backends as numeric-index only.
**How to avoid:** Preserve current `resolve_device()` behavior returning strings as-is for unmatched names.
**Warning signs:** Pi startup fails with device-not-found despite known good ALSA config.

### Pitfall 3: Selector behavior diverges from `--profile` intent
**What goes wrong:** Runtime picks backend from current host OS when profile explicitly says `windows`/`rpi`.
**Why it happens:** Using host detection too early.
**How to avoid:** Make `settings.platform` authoritative except `auto`.
**Warning signs:** Same profile chooses different backend depending on machine running tests.

### Pitfall 4: Backend errors lose actionable guidance
**What goes wrong:** Generic exceptions bubble up without remediation hints.
**Why it happens:** New backend not wrapped with `AudioDeviceError` parity.
**How to avoid:** Standardize on `AudioDeviceError` for startup failures in both backends.
**Warning signs:** Fatal logs without device id/context or suggestion text.
