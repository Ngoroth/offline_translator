<task type="auto">
  <name>Task 1: Execute pre-flight checks via SSH</name>
  <files></files>
  <action>
SSH into pi@translator and run pre-flight verification checks:

1. **Connect to Pi:**
   ```bash
   ssh pi@translator
   ```

2. **Check model files exist:**
   ```bash
   ls -la models/llm/Qwen3-0.6B-Q4_K_M.gguf
   ls -la models/tts/en_US-libritts_r-medium.onnx
   ls -la models/tts/ru_RU-denis-medium.onnx
   ```

3. **Check audio devices available:**
   ```bash
   arecord -l | grep -E "card [0-9]:"
   aplay -l | grep -E "card [0-9]:"
   ```

4. **Check evdev device exists and is readable:**
   ```bash
   ls -la /dev/input/event1
   test -r /dev/input/event1 && echo "READABLE" || echo "NOT READABLE"
   ```

5. **Check user in 'input' group:**
   ```bash
   groups | grep -q input && echo "INPUT GROUP OK" || echo "MISSING INPUT GROUP"
   ```

Print PASS/FAIL status for each check. Abort on any failure with detailed error and fix suggestion.
  </action>
  <verify>
All checks print [OK] or [PASS]:
- Model files exist and are readable
- Audio devices available (arecord -l shows capture, aplay -l shows playback)
- /dev/input/event1 exists and is readable
- User is in 'input' group
  </verify>
  <done>
SSH connection successful, all pre-flight checks pass. System ready for audio/numpad testing.
  </done>
</task>

<task type="checkpoint:human-verify">
  <name>Task 2: Verify audio I/O on target hardware</name>
  <files></files>
  <action>
Test audio recording and playback on the Pi:

1. **Record 3-second audio sample:**
   ```bash
   arecord -D plughw:1,0 -f S16_LE -r 16000 -c 1 -d 3 /tmp/pi_audio_test.wav
   ```

2. **Play back the recording:**
   ```bash
   aplay -D plughw:0,0 /tmp/pi_audio_test.wav
   ```

3. **Verify file was created:**
   ```bash
   ls -la /tmp/pi_audio_test.wav
   ```

Print status for each step. If arecord or aplay fails, print error and abort.
  </action>
  <how-to-verify>
1. Recording completes without error (3 seconds)
2. Playback command completes without error
3. YOU (the user) confirm you heard the audio played back through speakers/headphones

After playback, respond with:
- "heard" if you heard the audio clearly
- "silent" if playback completed but you heard nothing
- "failed" if playback command errored
  </how-to-verify>
  <what-built>
Audio recording captured 3 seconds from USB microphone at plughw:1,0. Audio played back through speakers at plughw:0,0. User must confirm playback was audible.
  </what-built>
  <resume-signal>Type "heard", "silent", or "failed"</resume-signal>
</task>

<task type="checkpoint:human-action">
  <name>Task 3: Verify numpad PTT input via evdev</name>
  <files></files>
  <action>
Run the existing hardware check script to test numpad PTT input:

```bash
cd /path/to/offline_translator
uv run python scripts/hardware_check.py
```

The script will prompt you to press numpad keys. Watch for event detection logs.
  </action>
  <what-needs-doing>
The hardware_check.py script will prompt you to press numpad buttons:

1. When prompted, press **numpad 5** (KP_5) to test Speaker A PTT
2. When prompted, press **numpad 6** (KP_6) to test Speaker B PTT

Watch the console output for lines like:
- "EVENT DETECTED: Role a PRESSED" (for KP_5)
- "EVENT DETECTED: Role b PRESSED" (for KP_6)
- "EVENT DETECTED: Role a RELEASED" (for key release)

The script validates that evdev captures your numpad input correctly.
  </what-needs-doing>
  <how-to-verify>
1. Script runs without errors
2. Pressing KP_5 logs "Role a PRESSED" event
3. Pressing KP_6 logs "Role b PRESSED" event
4. Key release events are also detected
  </how-to-verify>
  <resume-signal>Type "success" if both keys detected, or describe what failed
Examples: "KP_5 worked, KP_6 not detected" or "both keys worked"</resume-signal>
</task>
