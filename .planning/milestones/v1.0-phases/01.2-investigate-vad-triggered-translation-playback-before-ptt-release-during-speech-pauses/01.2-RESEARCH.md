## Summary

The codebase already contains the exact config concept this phase needs: `audio.playback_during_recording` exists in settings and defaults to `False` in both shipped profiles (`config.yaml`), and `SCENARIOS.md` already defines speaker mode (`false`) vs headset mode (`true`). This matches the user decision to reuse an existing mode and keep default OFF.

Current runtime behavior does **not** apply that setting: `TranslationPipeline._player_worker()` always plays as soon as chunks arrive, even while the PTT key is still held (`session.state` stays `LISTENING` until release). So early playback is effectively always enabled whenever VAD harvests while holding PTT. This is the core implementation gap for planning.

The safest architecture is a small gating change in playback consumption (not VAD timing): keep VAD harvest and pause threshold logic unchanged, keep queue order unchanged, and only permit playback during `LISTENING` when `audio.playback_during_recording` (or CLI runtime override) is true. This preserves existing pause behavior and avoids introducing new overlap/duck policies.

**Primary recommendation:** Implement a runtime playback gate using existing `audio.playback_during_recording`, add a runtime-only CLI override for it, and verify behavior with focused integration tests around pre-release playback and post-release flush order.

### Pattern 1: Runtime-only CLI override over persisted config
**What:** Keep persisted config value as baseline; apply CLI override in-process after loading settings.
**When to use:** Any launch-time behavior toggle that must not mutate `config.yaml`.
**Example:**
```python
# Source: src/app/main.py + Python argparse docs
args = parse_cli_args(argv)
settings = load_settings(profile_override=args.profile)
if args.playback_during_recording is not None:
    settings.audio.playback_during_recording = args.playback_during_recording
```

### Pattern 2: Gate playback consumption, not upstream production
**What:** Let STT/LLM/TTS continue; conditionally defer player execution during `LISTENING`.
**When to use:** Need to preserve VAD pause harvesting and ordering but control audible output timing.
**Example:**
```python
# Source: src/app/orchestrator/pipeline.py (player worker pattern)
if (not self.settings.audio.playback_during_recording) and self.session.state == SessionState.LISTENING:
    # Wait until release transitions state away from LISTENING
    await asyncio.sleep(0.01)
    continue
```

### Anti-Patterns to Avoid
- **Changing VAD threshold defaults:** Violates locked decision to keep pause timing unchanged.
- **Introducing new overlap policy:** Out of scope for this urgent phase.
- **Adding a second concept flag:** Conflicts with reuse-existing-mode decision.

## Common Pitfalls

### Pitfall 1: Assuming setting exists means behavior exists
**What goes wrong:** `audio.playback_during_recording` is present in config but currently unused in runtime playback path.
**Why it happens:** No reference to the field outside config model and YAML.
**How to avoid:** Add explicit reads in startup/pipeline and tests that assert audible behavior changes.
**Warning signs:** Grep shows only one usage in config model.

### Pitfall 2: Gating at the wrong stage
**What goes wrong:** Teams gate VAD harvest/queueing instead of playback and accidentally change pause semantics.
**Why it happens:** Easier to block earlier, but it alters pipeline throughput and chunk cadence.
**How to avoid:** Keep STT/LLM/TTS unchanged; gate only in player worker.
**Warning signs:** Fewer STT calls during hold compared to existing FR11 expectations.

### Pitfall 3: Runtime override accidentally persisted
**What goes wrong:** CLI mode leaks into YAML or profile defaults.
**Why it happens:** Writing config back or mutating source artifacts in startup path.
**How to avoid:** Apply override to in-memory settings object only.
**Warning signs:** `config.yaml` diff after running CLI.

### Pitfall 4: Memory growth during long hold sessions
**What goes wrong:** If playback is deferred while pipelines keep producing, `player_queue` can accumulate large audio chunks.
**Why it happens:** Queue is unbounded and current architecture allows background processing while holding PTT.
**How to avoid:** Plan explicit queue behavior assertions and pragmatic limits/metrics (at least logging) in tests.
**Warning signs:** Long hold causes growing queue length and delayed flush after release.
